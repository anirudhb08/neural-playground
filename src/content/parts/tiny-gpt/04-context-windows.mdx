Training anything means showing it a question, letting it answer, and then
telling it what the answer should have been. Repeat until it improves.

That plan needs two things this tutorial does not yet have. Part 03 built the
machinery for turning text into numbers; run a whole text through it and what
comes out is one unbroken run of integers, start to finish, with nothing marking
where anything begins or ends. There is not a question in it and not an answer.

So both have to be cut out of that run before a single step of training can
happen. Which means settling two things first: **how far back the model gets to
look** when it answers, and **where the right answer comes from** once it has
looked.

## How far back can it look?

The obvious answer is *everything written so far*, and it cannot be done.

A model is a fixed piece of arithmetic: the same multiplications, in the same
arrangement, on every input. So every input has to be the same size, every
time. "Everything so far" is one character at the start of a book and three
hundred thousand by the end, and no fixed arrangement is both.

So the size is chosen in advance and never changes. The model sees that many
characters and not one more. It is called the **context window**, and in code it
is usually `block_size`.

<div class="claim mt-7">
Everything before the window may as well not exist. The model cannot see it,
and has no way of knowing it is there.
</div>

That is the same limitation the bigram had, moved. A bigram's window is one
character wide. Nothing in this tutorial ever removes the wall — the rest of it
is about pushing the wall further back and using what is inside it better.

## And where does the right answer come from?

This is the harder half. A question is a slice of text, and slicing is easy. An
answer is what *should* come next — and normally somebody has to say so.

That somebody is expensive. In the [other tutorial](/neural-networks/02-your-alphabet/)
it was you: you drew each character and then told the network which one it was.
Every drawing needed a person. Scale that to the amount of text a language model
needs and the sums stop working long before the compute does.

So look again at what is actually being asked. Given `the ca`, what comes next?
The text says `t`. It says so by having a `t` sitting in the next position,
because somebody wrote the sentence and that is how the sentence goes.

Take a chunk one character longer than the window. Call the first part `x` and
the same run shifted one along `y`. Now `y[0]` is what followed `x[0]`, and
`y[1]` is what followed `x[0]` and `x[1]` together, and so on down the chunk —
so one chunk is not one training example. It is as many as the window is wide.

Widen the window and the count goes up with it, out of the same sentence. Move
the chunk and it is a different eight examples, out of the same sentence again.

## Nobody wrote the answers down

That is worth stopping on, because on screen it looks exactly like labelled
training data — a question, `the ca`, and an answer, `t`.

Nobody produced it. The label was already in the sentence, and shifting by one
is the whole of how it was extracted. There is no annotation step in this
project, and there never will be.

<div class="claim mt-8">
The text is its own answer key.
</div>

Learning this way — where the answers are recovered from the data itself rather
than supplied alongside it — is called **self-supervised** learning. The name
makes it sound like a technique. It is really just this: shift by one.

And it is the reason these models got as large as they did. Labelling is
usually what runs out first — before compute, before money, before ideas.
Remove it and any text at all becomes training data the moment you have it,
which is how anyone came to train on quantities nobody could have annotated in
a hundred lifetimes.

## The off-by-one worth being careful about

`y[3]` is the answer after seeing **four** characters, not three. It is the
character that follows `x[0]` through `x[3]` inclusive.

That is easy to nod along to and easy to get wrong in code, and getting it wrong
does not crash anything. Forget the shift and `y[i]` becomes `x[i]` — the answer
is the character the model was just shown, so it learns to copy its own input,
which it can do perfectly. Every measurement you have says training is going
beautifully. The model is useless. Data-pipeline mistakes are quiet in exactly
this way.

The last cell below does the boundary arithmetic for the same reason. With 49
characters and a window of 8, the largest legal starting point is 40 — because
`y` for that row has to reach index 48, which is the last one there is.

## Why several chunks at once?

One more idea and then the code. Training on one chunk at a time works and
wastes the machine: the arithmetic for one row of eight characters does not
come close to occupying a processor that is built to do thousands of such
things simultaneously.

So chunks are stacked. Pick several random starting points, cut a chunk at each,
and put them in a rectangle — `x` and `y` both come out as *rows × window*. This
is a **batch**, and the only thing the rows have in common is that they are
being processed together.

<aside class="aside measure mt-5">
The rows do not interact. Nothing from row 0 reaches row 3, and the model would
give identical answers if you ran them one at a time. Batching is a throughput
trick and nothing else — which is worth holding on to, because when attention
arrives in part 07 and characters genuinely do start affecting each other, it
will matter that they only ever do so *within* a row.
</aside>
